What it actually is

An MCP server is a small program the assistant runs — not you. You never launch it and never see it. You say “turn this into a PDF” in Claude; Claude calls the tool; the file is converted and the result lands beside the original on your own disk. No browser, no upload dialog, no tab.

One command, run in any terminal, from any folder:

claude mcp add --scope user diemdesk -- npx -y diemdesk-mcp

--scope user makes it available in every project. Without it you get local, which is that one folder only. Then /mcp inside Claude Code lists it. Claude Desktop takes a JSON block instead — both forms are on diemdesk.com/mcp-server.

Two silent failure modes. Claude Desktop reads its config once, at startup — a reload is not enough, you must quit completely. And a single trailing comma in that JSON stops the whole file being read, with no error shown anywhere.

Why nine and not a hundred

DiemDesk has 114+ tools. Most run in the browser and never touch a server — that is the whole product. Those have nothing for an MCP server to call: exposing them would mean uploading files to do work the machine already does locally and privately. It would trade the moat for a longer list.

So what is exposed is exactly the set that genuinely needs a server. list_local_tools is the honest half of that: without it, an assistant that cannot find “merge PDF” concludes DiemDesk does not have one. With it, the assistant says “that runs in your browser, here is the page” instead of guessing.

Who can use it

Already gated, and more tightly than you would expect. ocr_pdf is Pro-only — it is the most expensive thing we run for one person. The six conversions and web capture give free users 3 a day, keyed by IP, plus a 20-per-15-minute burst limit. The gate lives in utils/entitlement.js, shared by every router, so the MCP path cannot bypass what the website enforces.

DIEMDESK_TOKEN is a DiemDesk Pro token — nothing to do with npm or GitHub. It lifts the daily cap. Optional; add it with -e DIEMDESK_TOKEN=xxx before the --.

Recommendation: do not make it fully Pro-only. It contradicts the standing rule — gate scale, not quality — and the expensive tool is already gated. A wall on first use means install, hit wall, uninstall; directories also rank by adoption. This server’s job is distribution, not revenue.

The two registries

This caused genuine confusion, and it is worth stating plainly: two different things are called “publishing”.

npmMCP Registry
IsThe warehouse — where code is stored and installed fromThe catalogue — what lists MCP servers so people find them
Used bynpx, at install timeHumans browsing; clients seeking verified servers
HoldsThe actual filesMetadata only, pointing back at npm
Gives youInstallabilityDiscoverability

Publishing to npm alone puts the code somewhere people can install from and nowhere they can find. Nobody browses three million npm packages looking for MCP servers.

Why the name is com.diemdesk/mcp

The registry stops people claiming servers they do not own, and the name you may use is decided by how you proved ownership:

ProofName must start
GitHub device loginio.github.<username>/
DNS TXT recordcom.diemdesk/

Domain proof was chosen because it is the brand rather than a personal account, and it survives the GitHub username ever changing. Only someone controlling diemdesk.com’s DNS can add a record to it — that is the whole proof. Cost: one TXT record, added alongside the existing SPF and Google-verification records, never replacing them.

The TXT record goes on the apex — diemdesk.com, not _mcp-auth.diemdesk.com. MCP DNS auth is SPF-style, not DKIM-style. Wrong placement fails with a generic signature error that gives no hint of the real cause. If the key is ever rotated, delete the old record — a stale one is tried first and fails.
The signing key. mcp/mcp-registry-key.pem — Ed25519, gitignored along with *.pem, verified never committed. Anyone holding it can publish servers as com.diemdesk. It exists only on your laptop, and not in the private memory repo either. If lost: generate a new pair, replace the TXT record.

Four traps, each of which cost a cycle

1. The bin warning that looked fatal

Publishing warned “bin[diemdesk-mcp] script name index.mjs was invalid and removed” — which reads as though the executable entry had been thrown away. If true, npx -y diemdesk-mcp would not resolve and every instruction on the site would be wrong. It was not thrown away: npm normalises ./index.mjs to index.mjs and keeps it. Verified by packing, installing into a clean project, and running the generated shim. Write bin paths without ./ and the warning goes away.

2. The README that would have published blank

files listed README.md and the file did not exist. The npm page would have shipped empty — for a package advertised on the site, worse than no page. Anything in files must actually exist.

3. The version that lied

The handshake announced 0.1.0 while npm served 0.1.1. The number was typed by hand and had already drifted one release. Clients display that string to users. It now reads from package.json — which is the only reason 0.1.2 exists. Caught only by testing the published package; the working copy was correct throughout.

4. The one-line PR that was 3,938 lines

The awesome-mcp-servers PR opened as +3938 −3937 — the entire README rewritten, because core.autocrlf false was set after cloning, by which point CRLF was already on disk. A maintainer would have closed it on sight.

What makes this one nasty: git diff --stat reported “1 insertion” the whole time. Only gh pr view --json additions,deletions revealed it. Set both core.autocrlf false and core.eol lf before cloning, and always check the PR’s real numbers before calling it done.

The directories

Official MCP Registry live

Run by Anthropic and the MCP steering group; what clients query for verified servers. Currently in preview, so expect churn. Check the listing any time: 

curl "https://registry.modelcontextprotocol.io/v0/servers?search=diemdesk"
Always run mcp-publisher validate before publishing. It caught a 422 — description is capped at 100 characters and ours was 148 — without spending a publish. Nothing in the quickstart mentions that cap.

awesome-mcp-servers PR open

93k stars, actively maintained. One line added to File Systems, the section that already holds the PDF and OCR servers, placed alphabetically. Their CONTRIBUTING asks agent-authored PRs to append a robot marker for fast-tracking — used, and disclosed in the body rather than applied quietly.

Glama submitted

Submitted on the Server tab, which is correct — Connector is for deployed remote endpoints. Their notice says public submissions are reviewed before becoming visible, so expect a delay rather than an instant listing.

Smithery skipped, deliberately

Not blocked — wrong shape. smithery mcp publish takes a hosted URL or a bundle, and a search of their directory for “filesystem” returned 127 results, every one a cloud service: Google Drive, OneDrive, Cloudinary. Their pitch is “auth, credentials and sessions handled for you”.

DiemDesk’s server does the opposite: it reads a file from your disk and writes the result back beside it. Hosting that turns it into an upload service — the one thing the product exists not to be. Revisit only if Smithery adds first-class stdio listings.
