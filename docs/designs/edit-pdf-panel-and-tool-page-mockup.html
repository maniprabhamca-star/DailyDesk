1

Right-hand properties panel

Contextual card stack: active object, numeric X/Y/W/H, opacity, font match, Layers (reorder · hide · delete), align-to-page. Passed through the shell's existing properties prop — the same one Annotate and Redact already use.

Why it matters: Smallpdf and iLovePDF give you a floating toolbar and nothing else — no coordinates, no layer list. This is the "design-tool precision" half of the positioning, and it's the single biggest visible gap between Edit and the other two editors.

2

Context bar row

The shell's contextBar slot, collapsed by default. Find & replace lives here so it never competes with the main toolbar for space.

Why it matters: the toolbar already wraps to two rows on a laptop. Anything else added inline makes it worse; the context bar is the pressure valve that already exists.

3

Resize grip on added text boxes

Bottom-right grip, matching the one paragraphs, images and stamps already have. Drag scales the box; the Move pill stays above so the two never overlap.

Why it matters: added text is the only object on the page you can't resize by dragging — you have to find the toolbar's ± buttons. It reads as a missing feature, not a design decision.

4

Serif & mono font fidelity

Ship Liberation Serif + Liberation Mono TTFs and map them in RENDER_CSS, the way Helvetica already maps to Liberation Sans. Today only helvetica is mapped; times and courier have no bundled files and fall through to whatever the OS has.

Why it matters: pdf.js draws standard serif and mono with Foxit .pfb Type 1 files, which a browser can't load as a webfont. So on any Times-set document the edited text is drawn in the visitor's own Times New Roman while everything around it is Foxit Serif — a subtle mismatch that reads as sloppy. Licence check first: Liberation is OFL/GPL+FE.

5

Find & replace across the document

Runs over the paragraph blocks the detector already builds. Live match count, page chips, prev/next, replace one, replace all. Every replacement goes through the existing block-edit path, so export and undo need no new code.

Why it matters: no browser PDF editor has this. Acrobat has it behind a desktop install. It's the clearest "we do something they can't" line on the whole tool, and it's the one people search for.

6

Zoom controls bonus

The shell already accepts zoomLabel / onZoomIn / onZoomOut and no editor passes them. Wiring it up in Edit costs almost nothing and fixes a real problem on dense contracts.

Part B — what a tool page can show that nobody else does

Today every tool page is title → tool → three how-to steps → FAQ. That's the same page Smallpdf, iLovePDF and TinyWow all ship. Below are six blocks that are only truthful because of how the product is actually built — which is exactly why competitors can't copy them.

Strongest

Live upload counter

A real counter, wired to PerformanceObserver, showing network requests carrying your file. It stays at zero because it has to.

0 bytes of your file left this device

Why they can't: their number wouldn't be zero.

The Google Drive thing you were trying to remember

It was cloud import — pull a file straight from Google Drive or Dropbox into any tool, filed under Tier C in the Pro differentiator list. Worth being clear about what it is and isn't:

It is parity, not differentiation. Smallpdf and iLovePDF both have it. It's also the one feature on this page in real tension with the privacy story — the file would come down through Google's servers, and the OAuth scope alone will make a privacy-minded visitor flinch. If we build it, it belongs behind Pro, with the scope narrowed to a single user-picked file and stated plainly on the page.
